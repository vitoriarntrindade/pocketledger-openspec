# Observability Specification

## Purpose

Makes the running service's behavior investigable — who called what, how long it took, and why it failed — without needing to reproduce a problem locally, through correlated structured logs, metrics, and distributed tracing.

## Requirements

### Requirement: Structured Logging
The system SHALL emit structured (JSON) log entries, and each entry SHALL include a timestamp, a log level, the service name, the environment, and a message.

#### Scenario: Log entry contains required fields
- **WHEN** the application handles any request or performs any logged operation
- **THEN** the resulting log entry is valid JSON containing timestamp, level, service name, environment, and message

### Requirement: Request Correlation
Every HTTP request SHALL be assigned a request id: taken from an inbound correlation header when provided by the client, or generated by the application otherwise. This id SHALL appear in every log entry produced while handling that request and SHALL be returned to the caller via a response header.

#### Scenario: Generated id when none supplied
- **WHEN** a request arrives without a correlation header
- **THEN** the system generates a request id, includes it in the logs for that request, and returns it in the response header

#### Scenario: Supplied id is preserved
- **WHEN** a request arrives with a correlation header already set
- **THEN** the system uses that value as the request id for logs and the response header, instead of generating a new one

### Requirement: Sensitive Data Excluded From Logs
Logs SHALL NOT contain passwords, JWTs, secrets, credentials, or unnecessarily detailed financial data.

#### Scenario: Login attempt does not leak credentials
- **WHEN** a user submits a login request, whether it succeeds or fails
- **THEN** no log entry produced for that request contains the submitted password or the issued token

### Requirement: Log Level Discipline
The system SHALL distinguish expected validation or business-rule failures, which SHALL NOT be logged at ERROR level, from unexpected internal failures, which SHALL be logged at ERROR or CRITICAL level with enough context (including a stack trace) to investigate.

#### Scenario: Validation failure is not logged as an error
- **WHEN** a request fails because of a business-rule or input-validation violation (e.g. a non-positive amount)
- **THEN** the system logs the event below ERROR level

#### Scenario: Unexpected failure is logged with context
- **WHEN** the application encounters an unhandled internal error while processing a request
- **THEN** the system logs an ERROR (or CRITICAL) entry including a stack trace and the request's correlation id

### Requirement: HTTP Metrics
The system SHALL expose metrics counting HTTP requests and HTTP errors and measuring request latency, broken down by HTTP method, route, and status code. These metrics SHALL NOT use high-cardinality labels such as user id, request id, or arbitrary user-supplied values.

#### Scenario: Completed request reflected in metrics
- **WHEN** a request completes with a given method, route, and status code
- **THEN** the exposed metrics reflect that request under labels for method, route, and status code only

### Requirement: Business Metrics
The system SHALL expose counts of key business operations, such as transactions created and summaries requested.

#### Scenario: Business operation increments its metric
- **WHEN** a transaction is successfully created
- **THEN** the corresponding business-operation metric increases

### Requirement: Distributed Tracing
Every HTTP request SHALL produce a trace containing spans for the HTTP entry point, the main business operation it triggers, and any database calls the tracing instrumentation supports. Trace and span identifiers SHALL be correlatable with the logs produced for the same request.

#### Scenario: Trace correlates with logs
- **WHEN** a request produces both a trace and log entries
- **THEN** the trace id is present in those log entries, allowing the two to be correlated

### Requirement: Health and Readiness Endpoints
The system SHALL expose a health endpoint reporting whether the application process is running, and a separate readiness endpoint reporting whether its dependencies (at minimum, the database) are reachable. Both SHALL be distinct from the metrics endpoint.

#### Scenario: Health check while running
- **WHEN** the application process is running normally
- **THEN** the health endpoint reports a healthy status

#### Scenario: Readiness reflects database availability
- **WHEN** the database is unreachable
- **THEN** the readiness endpoint reports a not-ready status, distinct from the health endpoint's own status

### Requirement: Consistent Error Contract
Error responses SHALL use a consistent JSON structure and appropriate HTTP status codes, SHALL include the request's correlation id, and SHALL NOT expose stack traces or other internal implementation detail to the client.

#### Scenario: Unexpected error returns a safe response
- **WHEN** an unhandled internal error occurs while processing a request
- **THEN** the client receives a generic error response with an appropriate status code, a consistent error structure, and the request's correlation id, without any stack trace or internal detail

#### Scenario: Validation error returns a descriptive but safe response
- **WHEN** a request fails input validation or a business rule
- **THEN** the client receives a 4xx response with a consistent error structure describing what was invalid, without internal implementation detail
